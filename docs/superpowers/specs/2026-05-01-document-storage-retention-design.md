# Design: Document Storage + Retention

## Problem

The claim signing workflow needs to store and later prove the integrity of several document artifacts:

- generated unsigned claim packet PDF
- signed claim packet PDF
- signing completion certificate or equivalent provider proof
- audit-safe metadata tying those bytes to a claim, snapshot, signing attempt, and borrower

The current DocuSign/QuestPDF design leaves storage open as “local filesystem, database bytea, or object-storage abstraction.” That blocks implementation because storage choice affects encryption, schema, hashing, download authorization, retry behavior, local testing, and retention.

The system needs a storage boundary before the DocuSign spec can be revised safely.

## Decision

Use a **document storage abstraction with a local filesystem implementation for the POC**.

Store document bytes outside the relational database, and store metadata, hashes, ownership, lifecycle links, and retention fields in PostgreSQL.

This gives the POC a concrete implementation without binding application logic to local disk. A future object storage implementation can replace the byte store without changing claim-signing application use cases.

## Goals

- Store generated PDFs, signed PDFs, and completion certificates through one application abstraction.
- Store audit-safe document metadata in the database.
- Compute and persist SHA-256 hashes for every stored artifact.
- Link every artifact to `ClaimId`, `SnapshotVersion`, `SnapshotHash`, and document purpose.
- Enforce borrower ownership before download.
- Keep raw document bytes out of audit logs and normal application logs.
- Define local POC retention/delete behavior.
- Give signing lifecycle transitions a reliable way to know when signed documents are actually stored.

## Non-Goals

- Production object storage provisioning.
- Legal record retention policy beyond the POC.
- Virus scanning or DLP.
- User-facing document management beyond signed packet download.
- Storing original uploaded supporting document bytes.
- DocuSign webhook verification.
- DocuSign envelope creation.

This storage spec defines how those artifact references and hashes are represented.

## Artifact Types

Document artifact type values:

```text
GeneratedClaimPacket
SignedClaimPacket
SigningCompletionCertificate
```

Definitions:

- `GeneratedClaimPacket`: PDF bytes generated by QuestPDF from a claim snapshot before signing.
- `SignedClaimPacket`: PDF bytes returned by the e-signature provider after completion.
- `SigningCompletionCertificate`: provider-supplied completion certificate, audit certificate, or equivalent proof document.

The POC must store all three types when provider behavior supports them. If a fake provider is used, it must generate deterministic fake artifacts for all required types.

## Storage Architecture

### Application Boundary

Add a storage abstraction in the payment-protection application layer:

```csharp
public interface IClaimDocumentStore {
  Task<StoredClaimDocument> StoreAsync(
    ClaimDocumentToStore document,
    CancellationToken cancellationToken);

  Task<ClaimDocumentReadResult> OpenReadAsync(
    string documentId,
    string userId,
    CancellationToken cancellationToken);
}
```

Input model:

```csharp
public sealed record ClaimDocumentToStore(
  string ClaimId,
  string UserId,
  int SnapshotVersion,
  string SnapshotHash,
  ClaimDocumentType DocumentType,
  string ContentType,
  string FileName,
  byte[] Bytes,
  string? SigningAttemptId,
  string? ProviderEnvelopeId,
  string CorrelationId);
```

Output model:

```csharp
public sealed record StoredClaimDocument(
  string DocumentId,
  string ClaimId,
  string UserId,
  int SnapshotVersion,
  string SnapshotHash,
  ClaimDocumentType DocumentType,
  string StorageProvider,
  string StorageKey,
  string ContentType,
  string FileName,
  long ByteLength,
  string Sha256Hash,
  DateTimeOffset StoredAt);
```

### Infrastructure Boundary

Infrastructure provides:

```text
LocalFileClaimDocumentByteStore
EfClaimDocumentMetadataStore
ClaimDocumentStore
```

Responsibilities:

- `LocalFileClaimDocumentByteStore`: writes and reads bytes under a configured local root.
- `EfClaimDocumentMetadataStore`: persists metadata and ownership data.
- `ClaimDocumentStore`: orchestrates hash computation, byte write, metadata write, and read authorization.

Application use cases depend only on `IClaimDocumentStore`.

## Local Filesystem POC

Configuration:

```text
ClaimDocuments:Provider = LocalFile
ClaimDocuments:LocalRoot = .local/claim-documents
ClaimDocuments:RetentionDays = 30
```

Local storage key format:

```text
{userId}/{claimId}/{snapshotVersion}/{documentType}/{documentId}.pdf
```

Rules:

- local root must be outside source-controlled directories or ignored by git
- implementation must create directories as needed
- file writes must be atomic enough for POC: write to temp path, flush, then move to final path
- never serve arbitrary filesystem paths from request input
- metadata `StorageKey` is relative to configured root
- deletion/cleanup must only delete files under configured root

The implementation must add or verify a gitignore rule for the configured local root.

## Database Metadata Schema

Add table:

```text
claim_documents
```

Columns:

```text
id text primary key
claim_id text not null
user_id text not null
snapshot_version integer not null
snapshot_hash text not null
document_type text not null
storage_provider text not null
storage_key text not null
content_type text not null
file_name text not null
byte_length bigint not null
sha256_hash text not null
signing_attempt_id text null
provider_envelope_id text null
stored_at timestamptz not null
retention_until timestamptz null
deleted_at timestamptz null
delete_reason text null
created_by text null
correlation_id text null
```

Indexes:

```text
index claim_documents(user_id, claim_id)
index claim_documents(claim_id, snapshot_version)
index claim_documents(document_type, claim_id)
index claim_documents(provider_envelope_id)
index claim_documents(sha256_hash)
unique claim_documents(claim_id, snapshot_version, document_type, sha256_hash)
```

Rationale:

- `user_id, claim_id` supports borrower ownership checks.
- `claim_id, snapshot_version` supports lifecycle/status consistency checks.
- `provider_envelope_id` supports callback correlation.
- hash index supports audit lookup.
- uniqueness prevents accidental duplicate metadata rows for the same artifact bytes and purpose.

## Hashing

Every stored artifact must have a SHA-256 hash over the exact stored bytes.

Hash format:

```text
lowercase hex SHA-256
```

Rules:

- compute hash before metadata persistence
- persist hash with metadata
- include hash in audit events
- verify hash after read in tests
- do not rely on provider-reported hashes as the internal hash of record

The generated packet hash used by DocuSign must be the hash of the bytes actually sent to the provider.

## Encryption Expectations

### POC Local Filesystem

For local POC:

- no application-managed file encryption is required
- local files must remain outside git
- local files must not be logged
- local files must be stored under developer machine filesystem permissions
- PII risk must be documented in local setup notes

### Production Direction

The abstraction must allow a future provider with:

- storage-provider encryption at rest
- optional application-managed envelope encryption
- access logging
- lifecycle/retention policies
- signed URL generation

Production encryption is not implemented in the POC, but the application API must not prevent it later.

## Download Authorization

Endpoint shape:

```http
GET /api/claims/{claimId}/documents/signed
Authorization: Bearer <access-token>
```

POC behavior:

- stream the signed packet PDF from the API
- do not return filesystem paths
- do not return signed object-storage URLs in the POC

Rules:

- current user must own the claim
- claim must be `SignedDocumentsStored` or `Submitted`
- requested document must have `DocumentType = SignedClaimPacket`
- document metadata `UserId` and `ClaimId` must match current user and route claim
- deleted documents are not downloadable
- response content type is `application/pdf`
- response filename is deterministic and safe:

```text
claim-{claimId}-signed-packet.pdf
```

Download should write an audit event:

```text
SignedDocumentDownloaded
```

Audit event includes:

- `ClaimId`
- `UserId`
- `DocumentId`
- `DocumentType`
- `Sha256Hash`
- `Timestamp`
- `CorrelationId`

Audit event must not include document bytes.

## Retention And Delete Rules For POC

POC retention:

```text
RetentionDays = 30
```

Rules:

- set `RetentionUntil = StoredAt + RetentionDays`
- no automatic deletion job is required in first implementation
- provide a cleanup service method or script entry point that can delete expired local files later
- soft-delete metadata first by setting `DeletedAt` and `DeleteReason`
- delete local file only after metadata soft-delete succeeds
- never delete documents for claims in `Submitted` unless a manual cleanup command explicitly requests it

Deletion is not borrower-facing in the POC.

## Consistency Rules

### Store Operation

A document store operation must:

1. validate required metadata
2. compute SHA-256 over bytes
3. write bytes to the byte store
4. persist metadata row
5. return stored metadata

If metadata persistence fails after byte write:

- attempt best-effort byte cleanup
- return failure
- write no success audit event

If byte cleanup fails:

- log storage key and correlation ID
- do not log bytes
- leave claim lifecycle unchanged

### Lifecycle Gate

The claim lifecycle may transition to `SignedDocumentsStored` only when metadata exists for:

```text
GeneratedClaimPacket
SignedClaimPacket
SigningCompletionCertificate
```

for the same:

```text
ClaimId
SnapshotVersion
SnapshotHash
SigningAttemptId or ProviderEnvelopeId
```

If the provider does not supply a certificate in a future integration, that provider-specific decision must be explicit in the DocuSign/fake-provider spec. The default lifecycle gate requires it.

## API Design

### Download Signed Packet

```http
GET /api/claims/{claimId}/documents/signed
```

Responses:

| Condition | Response |
|---|---|
| unauthenticated | `401` |
| other user’s claim | `404` |
| claim not signed/stored | `409` |
| signed packet metadata missing | `409` |
| local file missing | `503` or `500` with retry-safe error |
| success | `200 application/pdf` |

Response headers:

```text
Content-Type: application/pdf
Content-Disposition: attachment; filename="claim-CLM-2026-000001-signed-packet.pdf"
```

### Internal Artifact Lookup

Application services need internal lookup by:

```text
ClaimId
SnapshotVersion
DocumentType
```

and by:

```text
ProviderEnvelopeId
DocumentType
```

These are not public borrower APIs for the first POC.

## Audit-Safe References

Use document metadata IDs and hashes as audit references.

Audit records should include:

```text
DocumentId
DocumentType
Sha256Hash
ByteLength
ContentType
StorageProvider
ClaimId
SnapshotVersion
SnapshotHash
```

Audit records should not include:

- `StorageKey` unless support/debug policy allows it
- raw PDF bytes
- base64 document content
- raw claim snapshot JSON

## Fake Provider Requirements

The fake signing provider used in CI must store artifacts through the same `IClaimDocumentStore` path as the real provider.

It must generate:

- deterministic generated packet bytes or use the QuestPDF-generated packet from the real renderer
- deterministic fake signed packet bytes
- deterministic fake completion certificate bytes

Tests must assert metadata and hashes are persisted for all three artifact types.

## Testing Strategy

### Application Tests

- store generated packet computes SHA-256 hash over exact bytes
- store signed packet persists metadata linked to claim/snapshot
- store certificate persists metadata linked to provider envelope
- empty bytes are rejected
- invalid content type is rejected
- metadata persistence failure after byte write attempts cleanup
- lifecycle gate rejects `SignedDocumentsStored` when one required artifact is missing

### Infrastructure Tests

- local byte store writes under configured root
- local byte store rejects path traversal storage keys
- local byte store reads back exact bytes
- metadata row persists all required fields
- duplicate same-purpose same-hash row is rejected by uniqueness constraint
- soft delete sets `DeletedAt` and prevents download

### API Tests

- signed packet download requires auth
- other-user claim download returns `404`
- download before `SignedDocumentsStored` returns `409`
- missing local file returns retry-safe server error
- successful download returns PDF content type and safe filename
- successful download writes `SignedDocumentDownloaded` audit event

### Frontend Tests

- download button visible only when backend `canDownloadSignedPacket` is true
- download starts a file response request to `/api/claims/{claimId}/documents/signed`
- download error does not change claim lifecycle status locally

4. Add local filesystem byte store implementation.
5. Add metadata store implementation.

## Impact On DocuSign Spec

This spec resolves these prior DocuSign blockers:

- storage backend for POC
- audit-safe document references
- document metadata schema
- SHA-256 hash storage
- signed packet download authorization
- generated/signed/certificate artifact lifecycle gates
- local retention/delete behavior

This spec does not resolve:

- DocuSign Connect verification
- webhook idempotency
- account/envelope correlation rules
- local webhook reachability
- envelope creation and recipient identity details

Those belong in the next spec: **Webhook + External Callback**.

## Acceptance Criteria

- Generated PDFs, signed PDFs, and completion certificates have a concrete POC storage path.
- Document bytes are stored through an abstraction, not directly by signing use cases.
- Metadata and hashes are stored in PostgreSQL.
- Signed packet download enforces borrower ownership and claim status.
- Raw bytes are not logged or embedded in audit records.
- POC retention is defined as 30 days with soft-delete metadata semantics.
- The lifecycle can reliably determine whether required signed artifacts are stored.
